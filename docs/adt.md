## Документация
В этом разделе описана функциональность, добавленная в проект `rukaml` в рамках учебной практики третьего семестра.<br/>
Модуль `Frontend.Parsing` далее называется парсером, модуль `Frontend.Inferencer` — тайпчекером.<br/>
Далее приводится объяснение принятых решений и выполняемых преобразований.<br/>

### Паттерн-матчинг
Поддерживаются выражения вида:
```OCaml
match expression with
| pattern1 -> expression1
| pattern2 -> expression2
| ...
| patternN -> expressionN
```
Парсер преобразует выражение выше в `PMatch(expression, (case1, cases))` где
- `case1 = (pattern1, expression1)`
- `cases = [ (pattern2, expression2); (pattern3, expression3); ...; (patternN, expressionN) ]`


Такое представление делает паттерн-матчинг с пустым набором case'ов невыразимым в терминах AST.<br/>


Тайпчекер преобразует `PMatch(expression, (case1, cases))` в `TMatch(expression_typed, (case1_typed', cases_typed'), type)` и при этом
1. проверяется, что возможна унификация `expesssion` и каждого паттерна `pattern1`, ..., `patternN` — выводится наиболее общий унификатор
2. для всех `K = 1..N` выводится тип `expressionK` в соответствии с типом, полученным ранее, окружение типов расширяется новыми идентификаторами, объявленными в `patternK`, что реализовано схоже с типизацией выражений вида `fun pattern -> expression`
3. проверяется, что возможна унификация каждого выражения `expression1`, ..., `expressionN` и выводится наиболее общий унификатор `type`, который и становится выведенным типом всего выражения `match-with`


В модуле `Middle.ANF` выполняется преобразование `TMatch` в так называемое Decision Tree (дерево выбора, диаграмма решений).<br/>
Дальнейшие модули уже не работают с `match-with` выражениями, они полностью заменяются на `if-then-else` конструкции.<br/>


Паттерн-матчинг может быть неполным, в таком случае в ветке `else` окажется примитив `match-failure`.<br/>

### Конструкторы

Можно считать, что у конструктора либо ноль аргументов, либо один аргумент (который может быть кортежем) и тогда его аргумент будет выражен через `option`.<br/>
Такое представление используется в `Frontend.Parsetree` и `Frontend.Typedtree`.<br/>
Можно считать, что у конструктора целое неотрицательное количество аргументов — тогда его аргументы представляются как `list`.<br/>
В ANFTree (представление программы, описанное в начале модуля `Compile_lib.ANF`) используется такое представление.<br/> Преобразование аргумента конструктора из `option` в `list` делается в `Compile_lib.ANF`<br/>


Для дальнейшей работы программы необходимы примитивы, которые позволяют получить тег конструктора и его аргументы.<br/>


Тег конструктора — уникальный в рамках типа идентификатор, который присваивается конструктору на этапе тайпчекинга.<br/>
Тег вычисляется в тайпчекере обычным счётчиком, поддерживаемым при обработке объявления типа.<br/>
Для конструктора `TConstruct(ident, expr_option, ty)` тегом будет `ident.id`<br/>
За взятие тега конструктора отвечает примитив `get_tag`, за взятие аргументов конструктора — примитив `field`.<br/>


В диаграммах решений, построенных из `match-with` выражений, сначала проверяется совпадение тегов конструкторов, а затем совпадение их аргументов.<br/>

### Объявления типов
Поддерживаются объявления алгебраических типов данных вида:
```OCaml
type ('a1, ..., 'aN) name =
| Constructor1 of core_type option
| Constructor2 of core_type option
| ...
| ConstructorN of core_type option
```
Результатом обработки одного объявления типа является одно значение типа `Frontend.Parsetree.type_declaration`.<br/>
`type_declaration` и `core_type` описаны в модуле `Frontend.Parsetree`.<br/>


Тайпчекер преобразует `core_type` в полиморфные по параметрам `'a1`, ..., `'aN` типы.<br/>
Тайпчекер для проверяет, что все используемые в выражениях конструкторы уже были объявлены и определяет ожидаемый тип их аргумента.<br/>
Реализовано это путём поддержания словарей в процессе всего вывода типов.<br/>
Словари хранятся в полях типа `Front.Typedtree.Type_env.t`:
- `env_constructors` — уже объявленные конструкторы (например `Cons`, `Nil`, `Some`, `None`)
- `env_types` — уже объявленные типы (например `'a list`, `('k, 'v) map`)
- `env_values` — схемы типов уже объявленных значений (`let`-связываний верхнего уровня)


Все три поля реализованы через тип `Ident_map.t` — конечное отображение с доменом `Frontend.Ident.t`.<br/>
`constructor_info` нужен, чтобы узнать по конструктору тип, в рамках которого конструктор был объявлен (ссылка на `type_declaration`), а также ожидаемый тип аргумента конструктора для унификации с типом аргумента, передаемого конструктору.<br/>


Предполагается, что все built-in типы определяются через `Frontend.Typedtree.type_declaration`, см. `typ_int`, `typ_unit` и другие объявления в `Frontend.Typedtree.Typeenv`.<br/>

### Списки как встроенный тип данных
В AST конструкторы списков имеют вид `EConstruct("[]", [])` и `EConstruct("::", ...)`.<br/>

В парсере поддерживается синтаксический сахар для списков, например:
```OCaml
[ x; y; z ]

x :: y :: z :: w

1 + 2 :: [ 3; 4 ]

match items with
| [] -> []
| hd :: tl -> f hd :: map f tl 
```


Список и его конструкторы поддерживаются тайпчекером как встроенный тип, то есть определены в коде как `Frontend.Typedtree.type_declaration` и добавляются в начальное окружение, см. `Frontend.Typedtree.Type_env.TypeList`.<br/>


В `pretty-printer`'ах по имени конструктора определяется, что он является встроенным конструктором для списков, см. `Frontend.PPrint` и `Fronend.PPrinttyped`.<br/>
